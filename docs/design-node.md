# UDA BIOMED — 設計稿萃取紀錄

本文件記錄 `src/styles/tokens.css` 每個值的來源。**所有色值皆為實際取樣，非目測。**
若之後有人想改 token，請先讀這裡，確認要改的是「取樣值」還是「推導值」。

---

## 取樣方法

設計稿為四張 PNG，皆為 `1536 × 1024`。本機無 PIL 與 ImageMagick，改用 ffmpeg 解碼：

```bash
ffmpeg -i web_img/<檔名>.png -f rawvideo -pix_fmt rgb24 <檔名>.raw
```

再以 Python 直接讀 raw RGB 逐像素分析，兩種取法分開處理：

- **純色區塊**（色帶、按鈕、圓形、底色）→ 對區域內像素做**量化眾數**（quantise step 4）。
  設計稿是算圖，帶有輕微雜訊，眾數比單點取樣穩定。
- **文字與線條** → 先取區域內亮度最低的 12% 像素（字身核心，排除反鋸齒邊緣），
  再對這些像素做量化眾數（step 6）。直接取最小值會過度飽和，直接取單點會取到反鋸齒。

亮度公式：`0.2126 R + 0.7152 G + 0.0722 B`

四張稿代號：`home` / `about` / `research` / `tech`（對應 web_img 內四個 uuid 檔名）。

## 元件慣例

### 卡片

- **沒有 1px border。** 白卡（`#ffffff`）放在近白底（`#fdfdfd`）上，靠柔和陰影分離。
- 掃描 research 卡片左緣（`y=830`，`x` 由 78 往右）得到連續漸層：
  `#fdfdfd #fdfdfd #fdfdfd #fcfcfd #fbfbfc #fafafb #f9f8f9 #f7f7f8 #f6f5f7 #f4f4f5` → 卡內 `#fefefe`

- 圓角實測 **4–5px**（掃 TL 角，對角線約跨 5 個像素）。

### 按鈕

- 首頁實心 CTA：高度實測 **56px**，圓角實測 **2–3px**（掃 TL 角，對角線僅跨 2–3 像素）。

- 首頁 hero 為雙按鈕：實心「OUR RESEARCH」+ 白底藍框「CONTACT US」。

### 導覽

- 當前頁底線實測 **3px**（research 頁 `y=97,98,99` 為 navy，`y=96` 與 `y=100` 已是反鋸齒）。
  `CLAUDE.md` 寫 2px，已在 token 改為 3px。

|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|

## 首頁 hero 遮罩（Step 3 實測）

### 為什麼不用 `CLAUDE.md` 建議的 55%–65%

規範寫「`--color-navy` 搭配 55%–65% 透明度」，但那是憑經驗給的區間。實測後**不合格**。

先量影片本身有多亮。以 3fps 取樣 24 個畫格、縮到 320×180，計算 WCAG 相對亮度：

| 區域 | 全片最亮像素 | 99 百分位 |
| --- | --- | --- |
| header 導覽帶（頂端 11% 高） | 0.975 | 0.964 |
| hero 文字區（左 55% 寬、中段） | **1.000** | 0.973 |

文字區存在**純白**畫面，所以遮罩必須以白底作為最壞情況設計。

白字疊在「navy 遮罩 over 全白畫面」上的對比：

| 遮罩不透明度 | 合成底色 | 白字對比 | AA 4.5:1 |
| --- | --- | --- | --- |
| 55% | `#738dac` | 3.42:1 | 未達 |
| 60% | `#6683a4` | 3.93:1 | 未達 |
| 65% | `#59789d` | 4.54:1 | 勉強 |
| **72%** | **`#476a92`** | **5.60:1** | **通過** |
| 80% | `#335986` | 7.17:1 | 通過（AAA） |

達 AA 的臨界值是 **64.7%**，規範區間有一大半不合格。

### 次要文字另立一個 token

`--color-on-navy-muted`（78% 白）在**純 navy 區塊**上是 10.73:1，沒問題；
但疊在遮罩合成色 `#476a92` 上只有 **3.93:1**，不合格。

臨界白度是 87.9%。取 88% 只有 4.51:1，餘裕僅 0.01，太緊，故取 **90%**，
另立 `--color-on-video-muted`。

### 定案

```css
--hero-overlay: rgba(0, 48, 104, 0.72);
--color-on-video-muted: rgba(255, 255, 255, 0.9);
```

最壞情況（全白畫面）下的實測結果：

| 元素 | 對比 | 餘裕 |
| --- | --- | --- |
| hero H1 白字 | 5.60:1 | +1.10 |
| header 導覽白字（13px） | 5.60:1 | +1.10 |
| header CTA 白字＋白框 | 5.60:1 | +1.10 |
| wordmark 上排白字 | 5.60:1 | +1.10 |
| hero 內文 90% 白 | 4.90:1 | +0.40 |
| wordmark 下排 90% 白 | 4.90:1 | +0.40 |

## 波浪路徑的產生方式

`src/components/HeroWave.tsx` 的 `d` 字串不是手捏的。

取「波浪色帶」一節實測的 16 個上緣座標點（1536 座標系，色帶下緣 y=643），
以 y=350 為 viewBox 上緣平移，再用 **Catmull-Rom 轉 cubic bezier**
（控制點 = `p1 ± (p2−p0)/6`）產生通過每一個取樣點的平滑曲線。

```
viewBox="0 0 1536 293"
```

`preserveAspectRatio="none"`，隨容器寬度拉伸，維持貼齊底部的行為。
高度 `clamp(56px, 12vw, 160px)`。

> 亮點色 `--color-accent-bright`）。那組幾何在稿中是算圖產生的，
> 無法從取樣還原，重畫等同於自行創作視覺。要不要做、要做成什麼樣，
> 需要先確認。

## 橘色強調色 `#fd7c06`（指定）

首頁主要 CTA 與輪播當前指示點。

`--color-orange: #fd7c06`，相對亮度 **0.353**，屬於亮色。因此：

- **白字疊上去只有 2.60:1，低於 WCAG AA 的 4.5:1。**
  依指示仍採用白字，實際畫面取樣為 **2.64:1**（與推算相符）。
  這是全站唯一未達 AA 的文字，記在這裡以免日後被當成疏漏。

  若要合格，兩條路：
  1. 文字改 `--color-primary-600`（`#0b2849`）→ **5.70:1**，橘色不變
  2. 橘色壓到 `#bc5c04` 以下 → 白字才過 4.5:1，但那已經是褐色，不再是這個橘
- 橘色按鈕面與圓點對背景，在**目前的背景濃度下約 1.9:1**，低於 UI 元件與
  圖形物件所需的 3:1。白色外框可以解決（外框對背景 6.86:1），**但依指示不加**——
  加過一次又移除，兩次都是指定。要合規的話：背景左側回到 86% 以上，或加回外框。

> **首頁中段那兩顆橘鈕已依指示改成藍鈕**（2026-09-11）：核心定位的 Learn more、
> 技術平台的 Global Disease Market Scenario Platform，都換成 `variant="primary"`
> （`#0f3661` 底、白字）。白字對藍底是 **12.21:1**，比原本的 2.60:1 好非常多，
> 上面那條「橘鈕上的白字」的例外因此只剩 hero 那一顆與輪播圓點。
>
> 按鈕面對背景的那一項沒有改善：`--color-primary` 疊在 hero 遮罩底色上是
> **2.03:1**，跟橘色的 1.9:1 同一個量級，一樣低於 3:1。要解這一項只有加外框
> 或反轉成白底（`onDarkSolid`，5.60:1）。

### 目前已知的三項不合規（皆依指示採用）

| 項目 | 實測 | 門檻 | 回復方式 |
| --- | --- | --- | --- |
| 橘鈕上的白字（現在只剩 hero 那顆） | 2.64:1 | 4.5:1 | 文字改 `--color-primary-600`（5.70:1） |
| 橘鈕／圓點對背景 | 約 1.9:1 | 3:1 | 背景左端回到 86%，或加回外框 |
| 12px eyebrow | 3.89:1 | 4.5:1 | 背景左端回到 66.6% 以上 |

這三項都是刻意的取捨，不是疏漏。日後跑無障礙檢測時請對照此表，
不要當成 bug 逕行修改。

### hero 兩顆按鈕的寬度

依指示收窄：`.actions > *` 的 `padding-inline` 由 Button 的 `md`（`--space-4`＝32px）
改成 `--space-3`（24px），兩顆各短 16px（實測 391→375、267→251）。
只改 hero 這兩顆，站上其他 `md` 鈕不動。

**寬度的大宗是標籤字數，不是內距。** 三次調整的過程：

| | 做法 | 左 | 右 |
| - | - | - | - |
| 原始 | `md` 內距 32px、`nowrap` | 391 | 267 |
| 收內距 | `--space-3`（24px） | 375 | 251 |
| 縮文案 | 左改「Explore the technology」 | 255 | 251 |
| 折兩排 | 文案還原、鎖 `width: 16rem` | 256×69 | 256×69 |
| **現況** | **內距再縮一階、`width: 14rem`** | **224×53** | **224×53** |

最後改成兩排（指定「可以變成兩排字嗎」）：`.actions > *` 拿掉 `nowrap`、
鎖 `width: 16rem` 逼出換行點（不寫死 `<br>`），文案因此還原成完整的
「Explore cancer detection technology」——不必再為了縮短犧牲字義。

兩個配套：

- Button 的 `md` 只有 `min-height: 56px`，第二排把高度撐開，所以補
  `padding-block` 與 `line-height: 1.35`，字才不會貼著上下緣
- `.actions` 的 `align-items` 由 `center` 改 `stretch`。左右排數可能不同，
  `center` 會讓兩顆一高一矮；`stretch` 讓矮的補到同高

最後依指示把周圍內距再縮一階：`padding-block` 8px、`padding-inline` 16px、
`width: 14rem`。**同時要把 `min-height` 從 Button `md` 的 56px 降到 44px**——
不降的話高度會卡在 56 的地板上，內距縮了也看不出差別。44px 是 CLAUDE.md 的
觸控目標下限，不能再低；實際高度 53px，仍在下限之上。
（14rem 之下右邊的「Business collaboration」也折成兩排，兩顆同為 224×53。）

## 首頁背景色調（左藍右透明）

鋪在固定的背景層上，貫穿整個頁面。

```css
linear-gradient(
  to right,
  rgba(15, 54, 97, 0.62) 0%,
  rgba(15, 54, 97, 0.58) 50%,
  rgba(15, 54, 97, 0.34) 72%,
  rgba(15, 54, 97, 0) 92%
)
```

**能淡到這裡的前提是內文改用「大字」規格。** WCAG 對 ≥18.66px 且粗體的文字
只要求 3:1（而非 4.5:1），因此 hero 內文與區塊 lede 都改為 `19px / 600`。
若把它們改回一般字級，這個濃度就不合格——一般字級的硬底線是 **66.6%**。

濃度是算出來的。內容都排在左欄，以影片最亮的畫面（相對亮度 1.000）為最壞情況：

| 位置 | 遮罩濃度 | 白字對比 | 大字門檻 3:1 | 一般字門檻 4.5:1 |
| --- | --- | --- | --- | --- |
| 左欄文字 x=14% | 61.0% | 3.89:1 | 通過 | 未達 |
| 左欄文字最右緣 x=50% | 58.0% | 3.54:1 | 通過 | 未達 |
| x=92% 之後 | 0% | — | — | — |

白色卡片（62%）在右側無遮罩處，疊在影片最暗畫面上時
navy 標題 4.56:1、內文 4.67:1，仍達 AA。

### 踩到的坑：`<picture>` 讓 `object-fit` 失效

`<img>` 包在 `<picture>` 內時，`<picture>` 預設 `display: inline` 且沒有高度，
`img { height: 100% }` 無從解析而退回 `auto`——照片只佔容器上緣一條
（375 寬時是 375×211 而不是 375×420），`object-fit: cover` 形同沒設。
必須補 `.media picture { display: block; width: 100%; height: 100% }`。

這個值不影響結果。

## 波浪色帶（`common_img/`）

**現行版本是 SVG 路徑，不用圖檔**（2026-09-06 改，依 `common_img/wave2.png`）。
下方關於去背 PNG 的整段是前一版的紀錄，保留是因為那些量測（alpha 漸變、白霧
殘留的成因與修法）之後若要再用有紋理的素材還會用到。

### 為什麼從圖檔改回 SVG

`wave2.png` 是**純圖形**：白底、深藍色塊、中間一條白色細線，沒有任何紋理或照片。
這種東西用圖檔沒有意義——

| | 圖檔（前一版） | SVG（現行） |
| - | ---- | ---- |
| 大小 | `wave.png` 150K ＋ `wave.webp` 94K | 內嵌路徑約 2.6KB |
| 縮放 | 拉大會糊 | 任何尺寸都銳利 |
| 換色 | 要重新輸出素材 | `currentColor`，改一行 CSS |

（前一版之所以用圖檔，是因為那個素材**有**分子與實驗器材的紋理，SVG 畫不出來。
`wave2.png` 沒有紋理，所以這個理由消失了。）

路徑不是手描的：逐欄掃 `wave2.png` 找出深藍區間的上下緣，取 25 個取樣點，
再用 Catmull-Rom 轉成三次貝茲曲線。深藍實測 `#0a3660`，與 `--color-navy`
（`#003068`）幾乎相同，直接吃 token。

兩條路徑（上面的細帶、底下的主體）中間**留空不填色**，露出的是頁面底色——
所以放在任何背景上都對，不必假設它是白的。內頁 hero 有照片時，
那條縫透出的就是照片本身。

viewBox `1400×342`，長寬比 **4.094**，`--wave-h` 因此改成
`clamp(96px, 24.4vw, 420px)`（24.4 ＝ 100 ÷ 4.094）。

`public/media/wave.png` 與 `wave.webp` 已刪除——沒有任何地方引用，
留著是每次部署多 244KB。素材原檔 `common_img/` 沒有動，要回去隨時可以。

### 前一版：去背 PNG 的處理紀錄

素材換過一次：先是白底的 `wave.jpg`（由我去背），後改用外部工具產出的
`removebackground1788274148867.png`（960×419 RGBA）。

### 已去背的 PNG 仍需三項處理

外部工具的 alpha 漸變品質好（過渡 0 → 0.08 → 0.50 → 0.89 → 0.99 → 1.00，
約 4px），色帶內部也完全不透明、紋理沒有被誤傷。但直接用會有三個問題：

| 問題 | 實測 | 處理 |
| ---- | ---- | ---- |
| 上下有大片透明餘量 | 上 150px、下 96px | 裁到 y 118–323，色帶才會貼齊 hero 下緣 |
| 最右一欄全透明 | 只有 x=959 | 裁掉，否則拉伸後右側出現缺口 |
| 白霧殘留 | alpha ≤ 31 的 1192 個像素中 1165 個偏白，平均 `#eff4f8` | alpha 沿用，只把顏色換成該欄的實色，共修 1927 個 |

第三項就是原本白邊的成因。**alpha 本身沒問題，問題在半透明像素的顏色
仍帶著被去掉的白底**——合成時那點白會浮出來。修法是保留工具算好的 alpha，
只替換 RGB。

輸出 `959×205`（長寬比 4.68），`wave.webp` 94K、`wave.png` 150K，
都是 lossless。webp 必須 lossless：有損的 `yuva420p` 會對 alpha 做色度
次取樣，在硬邊上重新長出光暈。

驗證：疊在 `#b03000` 上掃描上緣，8 個取樣點全部「無白邊」（最亮值 72–73，
橘底本身是 72）；右緣與下緣都確認貼滿。

### 波浪高度

`preserveAspectRatio="none"`——色帶必須貼齊容器兩側與下緣。

**回到 SVG 之後高度可以自由給。** 拉伸只會讓曲線變平緩，不會像圖檔那版
把 DNA 與器材的紋理壓扁，所以不必再綁著素材的原生比例。

現行值 `clamp(80px, 16vw, 280px)`（依指示調低）：

| 視窗 | 波浪高 |
| ---- | ---- |
| 390 | 80px（觸到下限） |
| 1512 | 242px |
| ≥1750 | 280px（封頂） |

16vw 的等效比例是 6.25，比 SVG 的原比例 4.094 平緩。

### hero 高度綁著波浪高度算

`.hero:has(.media)` 的 `min-height` 從固定值改成
`calc(var(--wave-h) + 淨高)`（窄螢幕 21rem、1024 以上 26rem）。

波浪是不透明色帶，蓋掉的就是照片下緣。固定 560px 時，1512 寬的波浪（242px）
會吃掉照片 43%（回報「波浪擋住圖片下面很多」）。寫成 calc 之後，
**不論之後波浪怎麼調，照片永遠留得下那段淨高**。

| 視窗 | hero | 波浪 | 照片淨高 | 被蓋 |
| ---- | ---- | ---- | ---- | ---- |
| 390 | 416（原 420） | 80 | 140 | 36% |
| 1512 | 658（原 560） | 242 | 417（原 318） | 37% |

窄螢幕的加項不能低於 21rem：先寫 15rem 時 hero 掉到 320px，
照片反而更小、被蓋的比例更高——改動要看的是淨高，不是 hero 總高。
歷來的值：純 SVG 時期 12vw → 圖檔時期 21.4vw（＝原比例 4.68）→
SVG 原比例 24.4vw（1512 寬時 369px，太厚）→ 現在 16vw。

原本是 `clamp(96px, 12vw, 160px)`。純色 SVG 時期怎麼拉都看不出來，
換成有紋理的圖之後，DNA、顯微鏡、燒瓶在桌機會被壓扁：

| 視窗 | 舊值 | 舊紋理比例 | 新值 | 新紋理比例 | 波浪佔 hero |
| ---- | ---- | ---------- | ---- | ---------- | ----------- |
| 375 | 96px | 120% | 96px | 120% | 23% |
| 768 | 96px | 58% | 164px | 100% | 39% |
| 1440 | 160px | 52% | 308px | 100% | 53% |
| 1920 | 160px | 39% | 411px | 100% | — |

**代價是版面重心下移**：1440 寬時波浪佔掉 hero 的 53%，照片與色帶各一半。
原始設計稿裡波浪只是底部收邊，不是主角。這是明確選擇後的結果，不是疏忽。

375 維持在 96px 下限（21.4vw 只有 80px，色帶會細成一條邊），

## 品牌鎖定圖（`public/brand/`）

來源是 `logo_img/logo2th/` 的兩張 1182×1182 JPG（指定改用這一版）。
JPG 沒有透明度，兩張都帶滿版底色，所以要自己去背與裁切。

輸出：`logo-full-blue.png`（深藍字）與 `logo-full-white.png`（白字），
兩張都是 **711×231**，`Header.tsx` 的 `width`／`height` 要跟著這個值走——
寫錯的話瀏覽器保留的版位比例不對，載入時整條 header 會跳一下。

### 去背的作法

不用 `colorkey`：那是硬門檻，反鋸齒的邊緣會留一圈色暈。改成**用「與底色的距離」
當 alpha**，顏色則整片填成品牌色——兩張都是單色標誌，這樣邊緣過渡是連續的。

```
alpha = clamp((dist - floor) / (max - floor)) ，dist = 與底色的最大通道差
```

三個實際踩到的細節：

- **底色取眾數，不取角落像素。** 白色版的 (0,0) 是 `#7987ba`（JPEG 邊緣雜訊），
  拿它當底色會讓整張圖都被判成前景
- **四邊各切掉 4px 再處理。** 兩張圖的最外圈有一條亮線（實測底列距離 221），
  不切的話裁切框會被撐到滿版——白色版第一次就跑出 1182×707
- **alpha 低於 8% 一律歸零**，去掉 JPEG 壓縮在筆畫周圍留下的淡霧

裁切框用「距離 > 50% 最大值」的像素決定，四邊各留 8px 邊距。

### 綁網域時遇到的白畫面：不是 base 的問題

第一時間會以為是 base 設錯（症狀一模一樣），但那次不是。判斷方法是**看線上的
HTML 本身**：

```
curl -s https://www.udabiomed.com/ | md5   # 805842ea…
md5 -q index.html                          # 805842ea… ← 一樣
md5 -q dist/index.html                     # 493e4e1e… ← 不一樣
```

線上服務的是 **repo 裡的原始 `index.html`**，不是 build 產物：
`%BASE_URL%` 沒有被取代、`<script src="/src/main.tsx">` 還在——那是 dev 用的
進入點，伺服器上根本沒有這個檔，所以什麼都跑不起來。

原因是 **Settings → Pages → Build and deployment 的 Source 變成
「Deploy from a branch」**，等於把 repo 當靜態檔直接發佈。這個專案用的是
Actions workflow（`actions/deploy-pages`），Source 必須是 **GitHub Actions**。

> 分辨方式：base 設錯的話，線上 HTML 會是 build 產物（有 hash 過的 assets 路徑），
> 只是路徑前綴錯而 404；Source 設錯的話，線上 HTML 直接就是原始碼那一份。
